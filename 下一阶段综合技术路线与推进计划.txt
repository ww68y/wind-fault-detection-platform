风机叶片缺陷检测工程 - 下一阶段综合技术路线与推进计划
生成日期：2026-06-04

一、当前项目阶段判断

当前工程已经不再是单纯的 YOLO 模型训练项目，而是已经形成了一个可以运行、可以演示、可以继续扩展的“风机叶片缺陷检测与本地推理展示平台”。

现阶段已具备的能力包括：

1. 已训练 YOLO 风机叶片缺陷检测模型；
2. 支持 4 类缺陷检测：crack 裂纹、hole 孔洞、spalling 剥落、corrosion 腐蚀；
3. 支持单张图片上传检测；
4. 支持批量图片上传检测；
5. 支持视频上传检测；
6. 支持视频关键帧展示；
7. 支持本地 FastAPI 服务；
8. 支持本地网页检测工作台；
9. 支持检测结果图展示；
10. 支持 detection_report.json 和 detection_report.md；
11. 支持历史记录查看；
12. 支持漏检样本整理；
13. 已经接入 DTU 1024 切片数据；
14. 已经完成 DTU 数据转换、切片和训练流程测试；
15. 已经具备 GPU 训练环境。

因此，下一阶段不应该推倒重做系统，也不应该从模型训练重新开始，而应该在现有系统基础上升级为“检测 + 风险判断 + 故障分析 + 运维建议”的平台。


二、下一阶段项目定位

建议下一阶段项目定位为：

风机叶片缺陷检测与多模态故障分析系统 v0.2

核心思想：

YOLO 负责发现缺陷；
规则系统负责判断风险；
故障分析模块负责解释问题；
网页负责展示完整检测与分析结果；
DTU 和 hard_cases 用于后续模型优化。

升级后的系统流程：

图片 / 批量图片 / 视频关键帧
    -> YOLO 缺陷检测
    -> 输出缺陷类别、置信度、检测框、缺陷数量
    -> 规则系统判断风险等级
    -> 故障分析模块生成解释和建议
    -> 输出故障原因、风险影响、运维建议、复检要求
    -> 网页展示 + 报告保存


三、综合后的推进原则

1. 不重做现有系统

保留现有检测接口、网页、数据集、训练结果、报告文件和历史记录功能。

2. 不急着接真实大模型

第一版先做 mock 故障分析模块，用规则和模板生成分析内容，先把“检测 -> 分析 -> 展示 -> 报告”的工程流程跑通。

3. 风险等级由规则系统判断

风险等级不要完全交给大模型。先根据缺陷类别、数量、置信度、多类别情况等规则判断风险等级。

4. 多模态分析模块负责解释，不负责重新检测

YOLO 的检测结果是主要依据，分析模块只基于检测结果、原图、检测结果图和报告生成解释与运维建议，不能凭空编造未检测到的缺陷。

5. DTU 暂时不直接融合

DTU 模型和当前 4 类模型不是同一套类别体系。当前阶段先评估 DTU 模型价值，不直接合并，不覆盖现有主模型。


四、建议新增工程结构

第一版建议新增 analysis 目录，而不是直接命名为 vlm。

原因是当前第一版并不真正调用多模态大模型，而是“规则风险评估 + mock 故障分析”。等流程稳定后，再在 analysis 目录中增加真实 VLM 客户端。

建议新增目录：

src\wind_fault\analysis

建议新增文件：

1. report_loader.py

作用：
读取检测任务目录中的 detection_report.json，提取 request_id、缺陷数量、缺陷类别、置信度、检测框、原图路径、结果图路径等信息。

2. risk_engine.py

作用：
根据 YOLO 检测结果判断风险等级。

3. prompt_builder.py

作用：
根据 detection_report.json 生成多模态提示词。第一版可以先作为预留模块，方便以后接真实 VLM。

4. mock_vlm_analyzer.py

作用：
根据缺陷类别、风险等级和检测结果，用固定模板生成故障分析内容。

5. analysis_report.py

作用：
保存 analysis_report.json 和 analysis_report.md。

6. analyzer.py

作用：
串联整个分析流程：
读取检测报告 -> 计算风险等级 -> 生成故障分析 -> 保存分析报告 -> 返回给接口。


五、风险等级规则设计

风险等级建议分为：

- 正常
- 待复核
- 低风险
- 中风险
- 中高风险
- 高风险

基础规则建议：

1. 未检测到缺陷：正常；
2. corrosion 腐蚀：低风险或中风险；
3. spalling 剥落：中风险；
4. hole 孔洞：中高风险；
5. crack 裂纹：中高风险；
6. 缺陷数量大于等于 3：风险提升一级；
7. 同一张图片出现多类缺陷：风险提升一级；
8. 置信度低于 0.60：标记为待人工复核；
9. 置信度高于 0.90：检测可信度较高；
10. 多个高置信度缺陷同时出现：高风险。

风险等级只做辅助判断，最终结论仍需要结合现场人工检查。


六、mock 故障分析模板设计

第一版不接真实大模型，而是根据缺陷类别生成固定分析内容。

1. crack 裂纹

可能原因：
- 长期疲劳载荷；
- 局部应力集中；
- 材料老化；
- 外物冲击损伤。

运维建议：
- 人工复核裂纹长度、方向和扩展趋势；
- 必要时降低负载或停机检查；
- 维修后上传复检图片。

2. hole 孔洞

可能原因：
- 外物冲击；
- 材料局部破损；
- 制造缺陷；
- 长期磨损。

运维建议：
- 检查孔洞深度和边缘扩展情况；
- 判断是否影响叶片结构强度；
- 必要时进行修补或更换。

3. spalling 剥落

可能原因：
- 表面涂层脱落；
- 局部结构损伤；
- 长期运行导致表面材料剥离。

运维建议：
- 检查剥落面积和范围；
- 判断是否存在继续扩展；
- 进行局部修补和表面防护处理。

4. corrosion 腐蚀

可能原因：
- 潮湿环境；
- 盐雾环境；
- 防护层失效；
- 长期环境侵蚀。

运维建议：
- 检查腐蚀范围；
- 判断是否已经影响材料强度；
- 进行除锈、防腐和涂层修复。

八、后端接口改造

保留现有接口：

POST /detect
POST /detect/batch
POST /detect/video

新增接口：

POST /analyze/{request_id}

接口作用：

根据已有检测任务的 request_id，读取该任务的 detection_report.json，生成故障分析结果。

接口流程：

1. 前端传入 request_id；
2. 后端找到对应检测任务目录；
3. 读取 detection_report.json；
4. risk_engine.py 判断风险等级；
5. mock_vlm_analyzer.py 生成故障分析；
6. 保存 analysis_report.json；
7. 保存 analysis_report.md；
8. 返回分析结果给前端。

这样可以实现“先检测，再分析”，并且不会拖慢原来的检测接口。

十一、视频关键帧分析

当前视频检测已经可以生成原视频、检测结果视频和关键帧。

下一步可以把视频关键帧接入故障分析，但不建议对每一帧都分析，只选择关键帧。

关键帧选择规则：

1. 取缺陷数量最多的关键帧；
2. 取置信度最高的关键帧；
3. 取不同缺陷类别的代表帧；

video_analysis_report.json

十二、DTU 模型评估与融合路线

当前 DTU 1024 切片数据已经接入，并且已经完成数据转换、切片和训练。

注意：

DTU 模型是另一套 5 类缺陷体系；
当前网页默认模型是 4 类缺陷体系；
两者不是同一个模型。

因此，下一步不要直接融合，应该先评估。

建议评估内容：

1. 当前 4 类模型在 DTU 图片上的效果；
2. DTU 模型在 DTU 图片上的效果；
3. DTU 模型在原 wind_blade_defect 图片上的效果；
4. 两套模型的类别是否冲突；
5. DTU 模型是否更擅长细小裂纹和长条形缺陷；
6. 是否有必要统一类别体系。

DTU 后续路线：

路线 A：双模型模式
网页中允许用户选择通用风机缺陷模型或 DTU 细小缺陷模型。

路线 B：统一类别后合并训练
将两个数据集映射到统一类别体系后训练 v0.2 模型。

路线 C：DTU 作为困难样本补充
从 DTU 中筛选漏检、误检、小目标样本，加入 hard_cases，补标注后微调当前模型。

当前最稳路线：

先走路线 C，再考虑路线 A 或路线 B。

十七、最终路线总结

综合两个方案后，现阶段最适合的技术路线是：

在现有图片、批量、视频检测系统后面新增“规则风险评估 + mock 故障分析”模块。

YOLO 负责发现缺陷；
规则系统负责判断风险；
故障分析模块负责解释故障并生成运维建议；
网页负责展示完整检测与分析结果；
DTU 和 hard_cases 用于后续模型优化。

一句话总结：

下一步最应该推进的是 /analyze/{request_id} 故障分析接口和网页端“生成故障分析”功能。先用 mock 分析跑通流程，再接真实多模态模型；先保持当前 4 类 YOLO 主模型稳定，再评估 DTU 模型是否用于细小缺陷增强或困难样本优化。
